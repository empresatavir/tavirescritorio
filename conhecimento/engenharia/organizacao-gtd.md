# Organização GTD

## Definição
O sistema GTD usa 7 categorias físicas ou digitais para organizar todas as ações e informações resultantes do processamento. Cada categoria representa um tipo específico de acordo consigo mesmo. A regra crítica: as categorias devem ser mantidas visualmente, fisicamente e psicologicamente separadas — quando categorias se misturam, o sistema perde confiabilidade e a mente retoma o trabalho de monitoramento.

## Mecanismo

### As 7 Categorias

**1. Projects List**

Qualquer outcome que requer mais de uma ação. Isso inclui desde "comprar novo laptop" até "lançar produto".

A lista de projetos não contém próximas ações — é um inventário de finish lines abertas. O propósito: garantir que cada projeto tem pelo menos uma próxima ação na Next Actions list. Sem isso, o projeto existe como commitment mas não como ação — cria open loop sem caminho de resolução.

Tamanho típico: 30-100 projetos para a maioria dos profissionais.

**2. Project Support Material**

Informação, planos e materiais de referência para projetos ativos. Organizado por projeto, não por ação. Pode ser pasta física, pasta digital, ou notebook.

Distinção importante: material de suporte não é a lista de projetos (que lista apenas o outcome) nem a lista de próximas ações (que lista apenas o próximo passo). É onde você guarda o "contexto" acumulado do projeto.

**3. Calendar**

Exclusivamente para três tipos de itens:
- *Ações time-specific*: compromissos em horário determinado (reuniões, chamadas agendadas)
- *Ações day-specific*: coisas que precisam acontecer em um dia específico mas não horário fixo
- *Informações day-specific*: dados relevantes para um dia (direções, quem vai estar onde)

**O que NÃO vai no calendário:** to-do lists diárias, ações "gostaria de fazer hoje", lembretes genéricos. O calendário é "território sagrado" — o que está lá, tem que ser feito naquele dia. Misturar a-ler-quando-der com compromissos fixos destrói a confiabilidade do calendário.

**4. Next Actions Lists**

O coração do sistema. Todas as próximas ações físicas e concretas para cada projeto e compromisso, organizadas por *contexto*.

Por que por contexto? Porque você só pode executar ações que o contexto permite. Quando está no telefone com 15 minutos disponíveis, quer ver *só* as ações que requerem telefone — não ter que filtrar mentalmente por toda a lista.

Contextos comuns:
- @Ligar / @Calls
- @Computador / @Online
- @Errandas / @Fora de casa
- @Casa
- @Escritório
- @Agenda [nome] — tudo para discutir na próxima conversa com alguém específico

**5. Waiting For**

Ações delegadas a outros, onde você está esperando resposta ou entrega. Cada item inclui: o quê, de quem, quando foi delegado.

Sem o Waiting For, delegações criam open loops que o cérebro monitora. Com o Waiting For, o item sai do radar ativo mas está capturado para follow-up no Weekly Review.

**6. Reference Material**

Informação sem ação associada que pode ser necessária no futuro. Sistema de referência geral: um único sistema A-Z alfabético. A regra de Allen: se leva mais de 60 segundos para arquivar algo, você vai empilhar em vez de arquivar.

Dois tipos: referência geral (um único arquivo A-Z) e suporte a projetos (organizado por projeto).

**7. Someday/Maybe List**

"Estacionamento" para coisas que você não quer fazer agora mas não quer perder. Livros para ler, viagens para fazer, habilidades para aprender, projetos futuros.

O Someday/Maybe resolve o dilema de "não quero me comprometer agora, mas também não quero jogar fora". A lista é revisada semanalmente no Weekly Review — você diz conscientemente "não essa semana" em vez de permitir que o item continue como open loop difuso.

### Por Que as Bordas Importam

Allen enfatiza que cada categoria deve ser mantida precisa e separada. Misturar categorias destrói a confiabilidade:

- Reference material no mesmo lugar que Next Actions → você vai ao arquivo não confiando que encontrou tudo
- Someday/Maybe items na Projects list → a Projects list parece esmagadora, itens sem próxima ação criam gaps
- Calendar entries misturadas com Next Actions → você não confia no calendário para saber o que "tem que acontecer hoje"
- Waiting For não separado das Next Actions → você repensa itens que não são seus para fazer

A consequência de bordas difusas: a mente percebe o sistema como não confiável e retoma o monitoramento manual — exatamente o que o sistema deveria eliminar.

### Listas vs. Pastas

O sistema GTD não especifica um medium — pode ser papel, digital, ou combinação. O que importa é que as categorias existam como entidades separadas e consultáveis. Papéis separados em pastas físicas, apps digitais como OmniFocus, Todoist, Notion, ou planilhas — todos funcionam se mantiverem a estrutura das 7 categorias com bordas limpas.

## Aplicações Práticas

### Configuração Inicial
- Criar as 7 categorias como listas separadas (podem ser digitais ou físicas)
- A Projects list é separada das Next Actions — confundi-las é o erro mais comum
- Criar pelo menos os contextos @Ligar, @Computador e @Errandas no início

### Manutenção Diária
- Verificar o calendário toda manhã: o que *tem* que acontecer hoje?
- Consultar as Next Actions lists no contexto atual: o que posso fazer agora?
- Não criar to-do lists diárias — o sistema já fornece o inventário

### Para Times
- O sistema de Waiting For aplicado a times: cada pessoa mantém sua lista de delegações com datas
- O Agenda list por pessoa resolve a tentação de interrupções constantes: acumular para a próxima conversa
- Projects list compartilhada (se necessário) separada das Next Actions individuais

## Contra-indicações
- Criar muitos contextos de Next Actions gera overhead — comece com poucos e adicione conforme necessário
- Someday/Maybe não é lixo — itens valiosos ficam lá. Não misturar com referência ou trash
- O Waiting For sem data cria false comfort — sempre incluir quando foi delegado
